# AI 페르소나 화재 대피 시뮬레이션

개화산역과 T자 복도 두 화면을 제공합니다. 개화산역은 개인별 실험 성향·제한된 공간 지식·관측·자신의 이동 경험으로 판단합니다. 기존 FDS 결과와 JuPedSim을 사용하며 원본 Nemotron 100명·UUID·원문, Jülich 시작 지연·기본 이동속도를 보존합니다.

## 실행

로컬 Ollama에 설치된 qwen3:4b를 사용합니다. 클라우드로 자동 전환하지 않습니다. PowerShell 7에서 scripts/start_local_ollama.ps1을 실행하면 기존 서버가 없을 때 시작합니다. 현재 GTX 1660 Ti 6GB에서 측정해 선택한 기본값은 Vulkan 실행기, Flash Attention, q8_0 KV 캐시, 동시 요청 2개, 입력 토큰 처리 단위 512입니다. f16과 q8_0의 속도 차이가 거의 없어 메모리를 덜 쓰는 q8_0을 선택했습니다. 모델 가중치 양자화와 KV 캐시는 다른 항목이며 모델 가중치는 바꾸지 않습니다.

```powershell
pwsh -NoProfile -File scripts/start_local_ollama.ps1 -Restart
```

새 환경에서만 이미지를 준비한 뒤 실행합니다. 기존 이미지가 준비된 환경에서는 다시 빌드할 필요가 없습니다.

```powershell
docker compose build app test
docker compose up -d app
```

- 개화산역: http://localhost:8010/
- T자 복도: http://localhost:8010/t-junction
- 앱은 프로젝트를 읽기 전용으로 연결하고 output만 쓰기 가능하게 연결합니다.
- FDS 누락·형상 불일치·해시 불일치 시 중단합니다. 합성 연기나 마지막 프레임 고정으로 대체하지 않습니다.

## 판단 흐름

원본 페르소나 → 실험 성향·초기 지식 → 개인 관측·지도 확장 → 사건 발생 시 Qwen 전략·기억·이동 의도 선택 → 개인 지도 안에서 실행 목표 계산 → 기존 JuPedSim·계단 이동 → 본인의 경험 기록.

Qwen을 새로 학습시키지 않고 고정된 로컬 모델로 원문과 상황을 해석합니다. 물리 엔진의 전체 지도와 개인의 판단 지식을 구분합니다. 최초 목표·층 도착·경로 비용·재탐색·응답 실패 시 기본 행동도 개인이 발견한 공간만 사용합니다. 미관측 경로의 거리나 다른 사람의 목적지·계획·기억을 제공하지 않습니다.

각 상황 판단 요청에는 **한 사람만** 넣습니다. 이전 대화 이력을 공유하지 않으며 본인의 최근 경험 최대 3개를 명시적으로 전달합니다. 정적인 성향 준비는 공개 원문 2명씩 처리하며 이동 중 기억·비공개 관측을 묶어 전달하지 않습니다.

같은 모의 시점의 개인별 상황 판단은 기본 2개 요청을 병렬 처리합니다. 모든 응답을 모은 뒤 원래 인물 순서대로 이동·기억을 적용하고, 한 사람의 실패는 해당 사람만 기본 행동으로 전환합니다. `PERSONA_EVAC_DECISION_WORKERS`로 동시 요청 수를 1~16 사이에서 조절하며 1은 순차 처리입니다. `PERSONA_EVAC_PROMPT_BATCH_SIZE`는 한 사람의 입력 토큰 처리 단위이며 기본 512, 허용 범위 32~2048입니다. 여러 사람의 정보를 하나의 프롬프트에 넣는 설정이 아닙니다. Ollama도 PowerShell 7에서 `./scripts/start_local_ollama.ps1 -Restart -Parallel 2`로 시작해야 실제로 동시에 추론합니다. 이미 실행 중인 앱이 있다면 코드 변경 적용을 위해 `docker compose restart app`을 실행합니다. `.env`의 설정을 변경했다면 `docker compose up -d app`으로 환경을 다시 적용합니다.

실행 결과의 `performance.decision_workers`는 요청 동시 처리 설정, `decision_prompt_batch_size`는 입력 토큰 처리 단위, `decision_batch_wall_s`는 캐시·응답 검증을 포함한 판단 묶음의 실제 대기 시간입니다. 기존 `llm_wall_s`는 각 추론 요청의 소요 시간 합계이므로 병렬 실행에서는 전체 실행 시간보다 클 수 있습니다. 시작 스크립트가 기록한 `output/ollama/runtime_config.json`의 실행기·KV 형식·Flash Attention·동시 처리 설정을 추론 설정과 응답 캐시 키에 포함합니다. 프로세스 번호·재시작 시각은 캐시 키에서 제외합니다. 기존 캐시는 남겨 두며 새 실행 설정과 섞지 않습니다. 모델·프롬프트·개인별 입력·응답 항목은 유지하지만 실행기의 수치 연산 차이로 새 응답이 이전과 완전히 같다고 보장하지는 않습니다.

2026-10-28 최초 설정의 서버 슬롯 1개까지 복원해 현재 설정과 다시 비교했습니다. 같은 모델·개인별 입력·출력 형식을 유지한 8개 상황을 설정별 2회씩 실제 추론했습니다. 각 측정 전에 서버 문맥 캐시를 초기화하고 같은 별도 상황으로 모델을 준비했으며, 모델 준비 시간과 응답 파일 캐시 재사용은 측정에서 제외했습니다.

| 실행 설정 | 8개 상황 평균 처리 시간 |
| --- | --- |
| 최초: CUDA · q8_0 KV · 입력 128 · 요청 1개 · 서버 슬롯 1개 | 39.96초 |
| 최적화 검증 당시: Vulkan · f16 KV · 입력 512 · 요청 2개 · 서버 슬롯 2개 | 26.64초 |
| 현재: Vulkan · q8_0 KV · 입력 512 · 요청 2개 · 서버 슬롯 2개 | 26.66초 |

최초는 39.85·40.07초, f16 최적화 검증 당시에는 26.53·26.75초로, 평균 약 33.3% 단축·처리량 약 1.50배였습니다. 이 비교에서는 전략 8/8, 이동 선택 7/8이 일치했고 실패는 없었습니다. 이전에 제시한 약 35%는 CUDA 서버 슬롯이 2개인 중간 상태와의 비교였으며, [최초·최적화 직접 비교](output/qa/local_tuning/initial_vs_current.json)는 f16 설정에서 수행한 원본 측정으로 보존합니다. 현재 기본 KV 형식은 이후 항목별 비교에서 속도가 거의 같았던 q8_0으로 변경했습니다. 원본 측정과 설정 변경은 [최적화 검증 보고서](output/qa/local_tuning/optimization_summary.json)에 기록합니다.

같은 8개 상황을 설정별 2회씩 추가 측정해 f16 검증 당시 설정에서 한 항목만 되돌린 [항목별 비교](output/qa/local_tuning/ablation_summary.json)도 수행했습니다. 실행기만 CUDA로 되돌리면 평균 38.67초로, Vulkan의 26.64초 대비 약 31% 차이가 났습니다. 입력 처리 단위만 128로 되돌리면 29.80초로 512의 효과는 약 11%였습니다. KV 캐시만 q8_0으로 바꾸면 26.66초로 f16의 26.64초와 사실상 같았습니다. 따라서 속도 개선의 주원인은 실행기, 다음은 입력 처리 단위이며, f16 전환의 독립적인 속도 개선은 확인되지 않았습니다. 각 수치는 f16 검증 당시 설정에서 한 항목씩 바꾼 효과로 서로 더할 수 없습니다.

KV 형식만 바꾼 동일 4096토큰·2슬롯 조건에서 KV 메모리는 f16 1152MiB → q8_0 612MiB로 약 47% 줄었습니다. 이는 KV 영역의 절감량이며 전체 GPU 메모리가 절반으로 줄어드는 것은 아닙니다. q8_0은 캐시를 양자화하므로 모델 선택이 f16과 완전히 같다고 보장하지 않으며, 기존처럼 실행 설정별로 응답 캐시를 분리합니다.

단순 병렬화만 시험한 기존 CUDA 4명 표본은 순차 12.63초·병렬 14.42초였습니다. CUDA 로그에는 이 GPU의 Tensor Core 부재로 성능이 최적이 아니라는 경고가 있습니다. Vulkan의 입력 512 중간 비교에서도 요청 1개는 26.97초·2개는 26.28초로 병렬화 자체의 추가 이득은 작았습니다. 출력 축약은 8개 중 7개의 전략이 달라져 앱에 반영하지 않았으며 벤치마크에만 남깁니다. 위 측정은 고정된 개인별 상황의 처리량 비교이고, 실제 계산에서 다른 모의 시점의 요청을 미리 묶지 않습니다. 전체 100명 시뮬레이션의 단축률을 보장하지 않습니다.

별도 6개 상황에서도 기존 CUDA 병렬 설정 30.66초 → Vulkan 최적화 병렬 설정 19.78초로 약 35% 짧았습니다. 두 표본의 전략은 14/14 일치했고 이동 선택은 11/14 일치했습니다. 판단 실패는 0건, 전체 회귀 테스트는 87개 통과했습니다. 출력 형식과 정보 분리를 유지해도 실행기의 수치 연산 차이로 모델 선택이 달라질 수 있으므로 새 응답을 별도 설정의 캐시에 기록합니다.

`python scripts/benchmark_local_inference.py --count 8 --batch-sizes 128 512 --workers 1 2 --reset-between-trials`로 새 응답 캐시에서 재측정합니다. 최초의 서버 설정은 `pwsh -NoProfile -File scripts/start_local_ollama.ps1 -Restart -Backend cuda_v13 -Parallel 1 -KvCacheType q8_0`이며, 최초의 앱 설정까지 재현하려면 `PERSONA_EVAC_DECISION_WORKERS=1`, `PERSONA_EVAC_PROMPT_BATCH_SIZE=128`도 적용해야 합니다. 다른 GPU에서는 실행기별 성능을 다시 비교해야 합니다.

100명 전체 시뮬레이션도 최초·최종 설정으로 각각 실제 실행했습니다. 같은 100명·FDS 화재·600초·실험 시드 20261027·고정한 동일 코드와 Docker 이미지에서, 준비된 성향은 공유하고 상황 판단의 응답 파일 캐시는 전부 사용하지 않았습니다.

| 항목 | 최초 설정 | 최종 설정 |
| --- | --- | --- |
| 실행기 | CUDA | Vulkan |
| 동시 요청 / 서버 슬롯 | 1 / 1 | 2 / 2 |
| 입력 처리 단위 | 128토큰 | 512토큰 |
| KV 캐시 | q8_0 | q8_0 |
| 실제 추론 횟수 | 696회 | 741회 |
| 추론 대기시간 | 57분 59초 | 38분 42초 |
| 전체 계산·결과 저장 시간 | 65분 23초 | 46분 45초 |

추론 대기시간은 33.25%, 전체 계산시간은 28.48% 줄었습니다. 추론 시간은 같은 모의 시점의 판단 묶음에서 응답을 기다린 실제 경과 시간이며, 병렬 요청별 시간을 중복 합산하지 않습니다. 모델 준비 시간은 제외했습니다. 두 실행의 코드·입력·모델 해시가 같고 응답 캐시 사용·판단 실패는 각각 0건입니다. 실행기 수치 차이로 판단과 이동이 달라져 추론 횟수 및 대피 완료 인원(85명 / 84명)도 달랐습니다. [100명 실측 비교](output/qa/full100/20261028T111153/comparison.json)와 [파일·조건 검증](output/qa/full100/20261028T111153/verification.json)에 원본 결과 경로와 측정 조건을 기록했습니다.

모델의 원래 선택, 전략에 자동 연결한 성향 근거, 비용 계산 결과, 실제 목표와 제약을 따로 저장합니다. 자동 탐색·막힌 경험 후 재탐색은 코드의 선택으로 기록합니다. 이를 Qwen이 직접 경로나 계단을 골랐다고 표시하지 않습니다.

## 성향·근거·재현성

정책은 [private_agent_policy.json](configs/agents/private_agent_policy.json), 원문 후보 추출·검증은 [experimental_profile.py](src/persona_evac/persona/experimental_profile.py)에 있습니다.

| 실험 성향 | 낮음 / 보통 / 높음의 정책값 |
| --- | --- |
| 혼잡 회피 | 혼잡 비용 0 / 12 / 36 |
| 대기 인내 | 인내 기준 3 / 8 / 16초 |
| 위험 회피 | 위험 비용 배율 1 / 2 / 4 |
| 탐색 적극성 | 탐색 보너스 2 / 6 / 12 |

정책값은 실험 가정이며 실제 사람에게서 측정한 성격·위기 대응 능력이 아닙니다. 선택 비용과 실제 소요 시간을 구분합니다.

- 스포츠·여행·직업·가족·취미 등의 원문에서 관련 표현을 검색합니다. 성향별 후보 최대 2개, 최대 140자의 정확한 부분 문자열을 제공합니다.
- Qwen이 근거를 해석하면 인용 ID·필드·원문·해시와 대피 성향으로 전이한 가정을 저장합니다.
- 근거가 없거나 불충분하면 UUID·실험 시드·프로필 정책 버전·성향명으로 독립 배정합니다. 분포는 낮음 25% / 보통 50% / 높음 25%, 기본 시드는 20261027입니다.
- 원문 사실·Qwen 해석 가정·실험 배정을 구분합니다. 배정 항목에는 인용을 만들지 않습니다.
- 후보 검색은 완전한 의미 검색이 아니므로 관련 서술을 놓칠 수 있습니다. 인용 검증은 문자열의 진위 검사이며 해석의 심리학적 타당성을 입증하지 않습니다.

프로필은 output/gaehwasan/private_profile_cache 아래 정책 버전 / UUID / 시드 / 입력 해시로 저장합니다. 원문·UUID·분포·배정 결과·인용을 다시 검증합니다. 나이·성별·스포츠 원문을 사용한 기존 시작 지연·속도 분류와 Jülich 수치는 유지합니다.

정책 버전은 experimental_traits_v2 / personal_space_v1 / occluded_perception_v1 / private_strategy_v2입니다. 결과와 응답 캐시에 버전·시드·정책 및 원문 해시를 포함합니다. 전체 결과는 관련 실행 코드 서명도 검사합니다.

## 초기 친숙도와 개인 관측

[gaehwasan_prior.json](configs/agents/gaehwasan_prior.json)은 제한적인 과거 구조 지식입니다. 서울 강서구의 province·district 또는 명시적 현재 거주 서술을 대리지표로 사용합니다. 부산 강서구·고향·직장·방문 정보를 구분하고 정확한 집 위치나 역까지의 거리를 추정하지 않습니다.

친숙한 인원에게 A_W·B_W·H_W·E_1의 일부 연결과 대략적인 과거 위치만 줍니다. 현재 화재·혼잡·통행 가능성이나 미관측 통로의 경로는 주지 않습니다. 원본 100명은 모두 초행이며 66번 부산 강서구를 서울로 처리하지 않았습니다. 거주자 기능은 원본 명단을 바꾸지 않고 별도 합성 자료로 검증했습니다.

[personal_space.py](src/persona_evac/integration/personal_space.py)는 벽·기둥·층·열차 벽과 문, 거리와 FDS 연기 가림을 검사합니다. 최대 18m 전방향 시야, 2m 관측 지도, 1초 갱신, 연기 광학 감쇠 예산 3, 광선 표본 간격 3m, 현재 관측 유효 시간 3초를 가정합니다.

각자 본 계단·통로·사람과 시점·출처를 기록합니다. 상대 속도는 자신의 연속 관측 위치로 추정합니다. 다른 사람의 목표속도·목적지·계획을 관측값으로 읽지 않습니다. 연결층은 과거 지식이나 직접 이동한 경험으로 배웁니다. 현재 모델에는 의사결정용 안내 표지가 없으며 화면 설명용 라벨은 전달하지 않습니다.

정확한 FDS 온도·소광계수는 물리 계산·연구자 표시에서 사용합니다. 판단에는 연기 없음/옅음/짙음/시야 차단, 평상시/따뜻함/강한 열감의 단계만 제공합니다. 먼 계단의 열감은 미관측입니다. 과거 관측과 현재 사실을 구분하고 지난 위험의 불확실성 비용을 따로 계산합니다.

## 사건·이동·물리 제약

## 재현·검사

성향 분류 기본값은 `configs/agents/private_agent_policy.json`의 `profile_classification.default_method`에 있는 `keyword_candidates`입니다. 기존 키워드 후보·Qwen 해석·UUID 시드 배정과 `experimental_traits_v2` 캐시는 그대로 사용합니다. 새 설정은 별도 해시를 사용하므로 기존 정책 해시·시드 결과·캐시 키를 바꾸지 않습니다.

`full_persona`는 UUID를 제외한 모든 원본 필드를 이름·값 그대로 Qwen에 전달합니다. 직접 서술(`direct`), 전체 문맥의 간접 추정(`contextual`), 정보 부족 가설(`hypothesis`)을 등급과 별도로 기록합니다. 사용 필드·실제 인용·해석 가정·정보 부족 여부도 저장합니다. LLM은 인용할 문자열 필드명(`quote_fields`)을 선택하고 코드가 해당 필드 전체를 수정 없이 실제 인용으로 연결합니다. 존재하지 않는 필드나 인용 텍스트는 거부하며 가설에는 인용이 없습니다. 입력 문장 선별이나 성향별 후보 수 제한은 없습니다. 근거 수준과 인용의 의미 적절성 자체는 LLM 판단입니다.

활성 결과를 바꾸지 않고 새 방식 100명을 준비하고 기존 캐시·5명 3회 추정을 비교하려면 다음을 실행합니다.

```powershell
docker compose exec -T app python scripts/prepare_private_profiles.py --method full_persona --count 100 --compare --repeat-count 5 --repeat-runs 2
```

별도 결과는 `output/gaehwasan/profile_preparations/full_persona/full_persona_traits_v1/profiles.json`, 집계·실패·반복 기록은 같은 폴더의 `report.json`입니다. 기본 캐시는 `private_profile_cache/full_persona_traits_v1` 아래에 원본·실험 시드·모델 이름/다이제스트·정책/프롬프트·스키마·추론 설정으로 구분됩니다. 반복 표본은 별도 `repeats` 경로에 저장됩니다. 같은 명령을 다시 실행하면 준비된 결과를 재사용합니다. 독립 재추론이 필요하면 별도 `--output-root`와 `--source`를 지정합니다.

기존 결과·캐시 해시 보존, 두 방식의 캐시 재사용, 원문·인용·정보 부족 실제 표본, 반복 등급 변화를 전수 검사하려면 `docker compose exec -T app python scripts/audit_profile_preparation.py`를 실행합니다. 이 검사는 추론이나 대피 계산을 호출하지 않습니다. 결과는 준비 폴더의 `verification.json`이며 변경 파일 목록과 한계도 포함합니다. 최초 보존 기준은 이번 구현 전에 기록한 `output/gaehwasan/profile_baseline_manifest.json`입니다.

선택 우선순위는 명시적 `--method`(준비 스크립트) / `--profile-method`(실행 CLI) / API의 `profile_method`, 환경변수 `PERSONA_EVAC_PROFILE_METHOD`, 정책의 기본값 순서입니다. API·CLI의 실행 요청은 대피 계산이므로 성향만 준비할 때는 위 스크립트를 사용합니다. 분류 방식·버전·프로필 정책 해시가 새 실행 결과에 기록됩니다. 전체 방식의 판단 프롬프트·캐시도 별도 경로를 사용합니다. 기존 프로필에는 호환성을 위해 메타데이터를 덧붙이지 않으며, 방식 표시가 없는 과거 결과는 기존 방식으로 읽습니다.

전체 입력은 자르지 않습니다. UTF-8 바이트 수를 이용한 보수적 입력 예산에 출력·스키마·메시지 여유를 포함하고 모델 지원 문맥을 확인합니다. 한도 초과는 `context_overflow`, 통신 오류는 `communication_error`, 형식·허위 인용 오류는 `invalid_output` 등의 기술 실패로 기록합니다. 형식 검증 재시도에도 원문 전체를 유지하며, 실패를 정상 추정이나 시드 배정으로 저장하지 않습니다. 오류 시 일부 완료된 사람의 캐시는 재사용 가능하지만 준비 보고서 상태는 실패입니다.

화면의 기존 개인 상세 근거 영역에 현재 방식·버전과 새 방식의 근거 수준·필드·인용·가정을 표시합니다. 저장 결과 조회(`GET /api/gaehwasan`)는 코드나 정책이 바뀌어도 활성 결과를 재계산하거나 덮어쓰지 않습니다. 원래 출처·코드 서명을 유지하고 응답의 `artifact_status`로 코드·정책 일치 여부를 제공합니다. 재계산은 명시적 실행 요청으로만 수행합니다.

프로젝트 루트에서 실행합니다. 기존 FDS 결과를 다시 계산할 필요는 없습니다.

개발 검사는 pytest를 사용합니다. 미관측 경로·위험·다른 사람 계획의 변경에 대한 불변성, 새 관측·막힌 경험, 거주지 구분, 중요 사건의 한도 예외, 측면 진입·충돌 회피를 검사합니다. test 이미지에 output을 연결하면 기존 FDS를 쓰는 검사도 실행합니다. 화면 검사는 scripts/verify_private_ui.cjs, T자 복도 검사는 scripts/verify_simulation_views.cjs이며 화면 캡처를 만들지 않습니다.
