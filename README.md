# AI 페르소나 화재 대피 시뮬레이션

개화산역과 T자 복도 두 화면을 제공합니다. 개화산역은 개인별 성향 6개·제한된 공간 지식·관측·자신의 이동 경험으로 판단합니다. 기존 FDS 결과와 JuPedSim, 원본 Nemotron 100명·UUID·원문을 사용합니다. 대피 반응 시간과 보행 속도는 LLM이 분류한 등급을 Jülich 경험 자료에 연결해 선택하고 원본 준비 파일은 보존합니다.

## 실행

처음 받는 컴퓨터에서는 Docker를 준비하고 아래 순서로 저장소와 필수 실행 데이터를 복원합니다. `runtime/simulation-data.zip`에는 현재 두 화면의 저장 결과, 100명 페르소나, 개화산역 FDS 변환 데이터와 성향·판단 캐시가 들어 있습니다. 이미지·PDF·PPT·비밀 설정·모델 가중치·FDS 원시 출력은 포함하지 않습니다.

```powershell
git clone --recurse-submodules https://github.com/taein0926/ai-persona.git
cd ai-persona
Copy-Item .env.example .env
docker compose --profile setup run --rm --no-deps bootstrap
docker compose build app test
docker compose up -d app
```

코드·지도·정책과 일치하는 저장 결과를 재생할 때는 Ollama가 필요하지 않습니다. 현재 포함된 역 대피 결과는 최신 코드보다 이전에 계산된 자료여서 `/api/gaehwasan`이 `station_result_outdated`(HTTP 409)로 차단합니다. 초기 지도·인원 설정과 FDS 입력은 복원되지만 최신 역 대피 결과를 보려면 아래의 모델과 Ollama를 준비하고 명시적으로 새 계산을 실행해야 합니다. 결과 서명을 바꾸거나 읽기 요청으로 자동 재계산하지 않습니다. T자 복도의 저장 결과는 별도로 조회합니다.

복원 명령은 파일 해시를 검사하며 기존 파일의 내용이 다르면 덮어쓰지 않고 중단합니다. 새 폴더에서 실행하세요. Python 3.12가 설치되어 있다면 `python scripts/runtime_data.py install`로도 복원할 수 있으며, 복원 후 `python scripts/runtime_data.py verify`로 무결성을 검사합니다. 포함된 성향·판단 캐시는 저장 당시의 모델·정책에 해당하며 현재 설정과 맞지 않거나 없는 캐시는 새 추론이 필요합니다. 새 컴퓨터의 모델 버전이나 하드웨어가 다르면 새 추론 결과와 속도가 기존 실행과 같다고 보장하지 않습니다.

기본 모델은 로컬 Ollama의 **Gemma 4 E2B (`gemma4:e2b-it-qat`)**입니다. `.env`의 `OLLAMA_MODEL`이 사전 준비와 실시간 개인별 판단에 공통으로 적용되며, 미설정 시 코드도 같은 모델을 선택합니다. 클라우드로 자동 전환하지 않습니다. PowerShell 7에서 scripts/start_local_ollama.ps1을 실행하면 기존 서버가 없을 때 시작합니다. 현재 GTX 1660 Ti 6GB에서 선택한 기본값은 Vulkan 실행기, Flash Attention, q8_0 KV 캐시, 동시 요청 2개, 입력 토큰 처리 단위 512입니다. q8_0은 KV 캐시 형식이며 모델 가중치 양자화와는 별개입니다.

```powershell
pwsh -NoProfile -File scripts/start_local_ollama.ps1 -Restart
pwsh -NoProfile -File scripts/verify_local_ollama.ps1 -Warmup -Model gemma4:e2b-it-qat
```

Vulkan 장치 번호는 바뀔 수 있어 기본값은 시작할 때마다 NVIDIA 장치를 탐색하는 방식입니다. 이전 번호를 재사용하지 않으며 실제 NVIDIA Vulkan 탐색을 확인하지 못하면 시작을 중단합니다. `-VulkanDevice`는 수동 지정이 필요할 때만 사용합니다. 긴 추론 전에 검증 스크립트로 실제 서버 PID·모델·전체 층 GPU 적재·두 슬롯·q8_0·Flash Attention을 확인합니다. 데스크톱 Ollama 앱이 별도 서버를 다시 띄워 설정이 달라지면 검증에서 중단합니다.

이번에 확인한 Ollama 0.40.13은 `qwen35` 아키텍처의 병렬 요청을 지원하지 않아 `qwen3.5:2b`를 실제 1슬롯으로 실행합니다. 서버 기본값 2슬롯과 구분하며, 이 모델을 확인할 때는 `pwsh -NoProfile -File scripts/verify_local_ollama.ps1 -Warmup -Model qwen3.5:2b -ExpectedParallel 1`로 예외를 명시합니다. Qwen3·Gemma는 기본 검증값 2슬롯을 사용합니다.

새 환경에서만 이미지를 준비한 뒤 실행합니다. 기존 이미지가 준비된 환경에서는 다시 빌드할 필요가 없습니다.

```powershell
docker compose build app test
docker compose up -d app
```

- 개화산역: http://localhost:8010/
- T자 복도: http://localhost:8010/t-junction
- 앱은 프로젝트를 읽기 전용으로 연결하고 output만 쓰기 가능하게 연결합니다.
- FDS 누락·형상 불일치·해시 불일치 시 중단합니다. 합성 연기나 마지막 프레임 고정으로 대체하지 않습니다.

추론 제공자는 로컬 Ollama만 지원합니다. 초기 반응·보행·친숙도 분류는 `llm/baseline_profile.py`, 성향 6개 분류는 `persona/full_profile.py`, 상황 판단은 `llm/private_decisions.py`에 있습니다. `llm/common.py`에는 기존 준비 자료를 읽는 공통 캐시 형식이 남아 있으며 새 프롬프트·스키마의 응답은 별도 키로 저장합니다. `mock`는 고정 합성 자료의 결합·회귀 테스트용입니다. 클라우드 SDK·제공자·실행 서비스와 사용하지 않는 API 키 설정은 제거했습니다.

T자 복도 성향 준비는 `docker compose run --rm ollama-experiment`로 실행합니다. 설정은 `configs/experiments/mvp_ollama.json`이며, 기존 FDS 변환·재생 자료와 연결된 `t-junction-mvp-openai` 산출물 폴더명과 과거 출처 표기는 읽기 호환성을 위해 유지합니다. 코드 서명 변경은 정상적으로 감지하며 기존 계산 결과의 서명을 새 코드에 맞춰 바꾸지 않습니다.

## 판단 흐름

2026-10-30 같은 실제 기록 40개를 두 번 비교했을 때 모델 준비 시간을 제외한 평균 처리 시간은 Qwen3:4b 206.6초, Gemma 4 E2B 116.4초, Qwen3.5:2B 142.9초였습니다. 이 비교는 당시 네 성향과 근거를 포함한 이전 입력을 고정한 결과이며, 현재 여섯 성향·등급 전용 입력의 전체 실행 시간을 뜻하지 않습니다. 현재 세 추론 경로의 Gemma 연결은 한 사람에 대한 실제 호출로 별도 확인했습니다.

원본 페르소나 → Gemma의 사전 분류와 실측 기반 초기값 → 개인 관측·지도 확장 → 사건 발생 시 Gemma의 전략·기억·이동 의도 선택 → 개인 지도 안에서 실행 목표 계산 → 기존 JuPedSim·계단 이동 → 본인의 경험 기록.

사전 준비에서는 Gemma가 원문 전체를 읽어 반응·보행 범주와 역사 친숙도, `full_persona`의 여섯 행동 성향을 분류합니다. 반응시간(초)과 목표 보행 속도(m/s)는 모델이 직접 만드는 값이 아니라 해당 범주의 Jülich 실측 자료에서 재현 가능한 방식으로 선택합니다. 친숙도는 초기 계단 위치·층 연결 기억을 정하며 현재 화재·혼잡을 알려 주지는 않습니다. 실시간 판단에는 성향 등급과 본인 관측·기억·가능한 선택지만 전달합니다.

모델명이나 가중치 해시가 달라지면 사전 기초 분류를 갱신하고, 성향·상황 판단 캐시는 모델별로 구분합니다. 기존 모델의 결과를 Gemma 결과로 이름만 바꾸지 않습니다. `--qwen`, `behavior_mode="qwen"`, `nemotron_qwen_empirical`, `qwen_interpretation`은 호환성을 위한 기존 식별자이며 실제 모델은 `OLLAMA_MODEL`과 각 결과의 모델명·해시로 확인합니다. 과거 측정·출처 기록은 당시 모델명으로 보존합니다.

기존 분류를 삭제하면 원본 페르소나와 자료 출처를 유지하고 `classification_pending`으로 표시합니다. 분류·선택된 실측 초기값은 화면에서 ‘계산 대기’로 표시하며, 초기값이 없는 상태로 물리 시뮬레이션을 실행하지 않습니다. `prepare-station-personas` 또는 명시적인 로컬 LLM 계산에서 Gemma로 다시 준비합니다. 실행 데이터 묶음에도 삭제 후 상태를 반영해 복원 시 이전 분류가 되살아나지 않도록 합니다.

고정된 로컬 모델로 원문과 상황을 해석합니다. 물리 엔진의 전체 지도와 개인의 판단 지식을 구분합니다. 최초 목표·층 도착·경로 비용·재탐색·응답 실패 시 기본 행동도 개인이 발견한 공간만 사용합니다. 미관측 경로의 거리나 다른 사람의 목적지·계획·기억을 제공하지 않습니다.

각 상황 판단 요청에는 **한 사람만** 넣습니다. 이전 대화 이력을 공유하지 않으며 본인의 최근 경험 최대 3개를 명시적으로 전달합니다. 현재 전체 원문 기반 초기 분류도 한 사람씩 처리합니다. 과거 키워드 후보 방식의 공개 원문 2명 묶음은 비교·호환용으로 남아 있으며 이동 중 기억·비공개 관측을 묶어 전달하지 않습니다.

같은 모의 시점의 개인별 상황 판단은 기본 2개 요청을 병렬 처리합니다. 모든 응답을 모은 뒤 원래 인물 순서대로 이동·기억을 적용하고, 한 사람의 실패는 해당 사람만 기본 행동으로 전환합니다. `PERSONA_EVAC_DECISION_WORKERS`로 동시 요청 수를 1~16 사이에서 조절하며 1은 순차 처리입니다. `PERSONA_EVAC_PROMPT_BATCH_SIZE`는 한 사람의 입력 토큰 처리 단위이며 기본 512, 허용 범위 32~2048입니다. 여러 사람의 정보를 하나의 프롬프트에 넣는 설정이 아닙니다. Ollama도 PowerShell 7에서 `./scripts/start_local_ollama.ps1 -Restart -Parallel 2`로 시작해야 실제로 동시에 추론합니다. 이미 실행 중인 앱이 있다면 코드 변경 적용을 위해 `docker compose restart app`을 실행합니다. `.env`의 설정을 변경했다면 `docker compose up -d app`으로 환경을 다시 적용합니다.

실행 결과의 `performance.decision_workers`는 요청 동시 처리 설정, `decision_prompt_batch_size`는 입력 토큰 처리 단위, `decision_batch_wall_s`는 캐시·응답 검증을 포함한 판단 묶음의 실제 대기 시간입니다. 기존 `llm_wall_s`는 각 추론 요청의 소요 시간 합계이므로 병렬 실행에서는 전체 실행 시간보다 클 수 있습니다. 시작 스크립트가 기록한 `output/ollama/runtime_config.json`의 실행기·KV 형식·Flash Attention·동시 처리 설정을 추론 설정과 응답 캐시 키에 포함합니다. 프로세스 번호·재시작 시각은 캐시 키에서 제외합니다. 기존 캐시는 남겨 두며 새 실행 설정과 섞지 않습니다. 모델·프롬프트·개인별 입력·응답 항목은 유지하지만 실행기의 수치 연산 차이로 새 응답이 이전과 완전히 같다고 보장하지는 않습니다.

2026-10-28 최초 설정의 서버 슬롯 1개까지 복원해 현재 설정과 다시 비교했습니다. 같은 모델·개인별 입력·출력 형식을 유지한 8개 상황을 설정별 2회씩 실제 추론했습니다. 각 측정 전에 서버 문맥 캐시를 초기화하고 같은 별도 상황으로 모델을 준비했으며, 모델 준비 시간과 응답 파일 캐시 재사용은 측정에서 제외했습니다.

| 실행 설정 | 8개 상황 평균 처리 시간 |
| --- | --- |
| 최초: CUDA · q8_0 KV · 입력 128 · 요청 1개 · 서버 슬롯 1개 | 39.96초 |
| 최적화 검증 당시: Vulkan · f16 KV · 입력 512 · 요청 2개 · 서버 슬롯 2개 | 26.64초 |
| 현재: Vulkan · q8_0 KV · 입력 512 · 요청 2개 · 서버 슬롯 2개 | 26.66초 |

최초는 39.85·40.07초, f16 최적화 검증 당시에는 26.53·26.75초로, 평균 약 33.3% 단축·처리량 약 1.50배였습니다. 이 비교에서는 전략 8/8, 이동 선택 7/8이 일치했고 실패는 없었습니다. 이전에 제시한 약 35%는 CUDA 서버 슬롯이 2개인 중간 상태와의 비교였으며, [최초·최적화 직접 비교](output/qa/local_tuning/initial_vs_current.json)는 f16 설정에서 수행한 원본 측정으로 보존합니다. 현재 기본 KV 형식은 이후 항목별 비교에서 속도가 거의 같았던 q8_0으로 변경했습니다. 원본 측정과 설정 변경은 [최적화 검증 보고서](output/qa/local_tuning/optimization_summary.json)에 기록합니다.

같은 8개 상황을 설정별 2회씩 추가 측정해 f16 검증 당시 설정에서 한 항목만 되돌린 [항목별 비교](output/qa/local_tuning/ablation_summary.json)도 수행했습니다. 실행기만 CUDA로 되돌리면 평균 38.67초로, Vulkan의 26.64초 대비 약 31% 차이가 났습니다. 입력 처리 단위만 128로 되돌리면 29.80초로 512의 효과는 약 11%였습니다. KV 캐시만 q8_0으로 바꾸면 26.66초로 f16의 26.64초와 사실상 같았습니다. 따라서 속도 개선의 주원인은 실행기, 다음은 입력 처리 단위이며, f16 전환의 독립적인 속도 개선은 확인되지 않았습니다. 각 수치는 f16 검증 당시 설정에서 한 항목씩 바꾼 효과로 서로 더할 수 없습니다.

KV 형식만 바꾼 동일 4096토큰·2슬롯 조건에서 KV 메모리는 f16 1152MiB → q8_0 612MiB로 약 47% 줄었습니다. 이는 KV 영역의 절감량이며 전체 GPU 메모리가 절반으로 줄어드는 것은 아닙니다. q8_0은 캐시를 양자화하므로 모델 선택이 f16과 완전히 같다고 보장하지 않으며, 기존처럼 실행 설정별로 응답 캐시를 분리합니다.

단순 병렬화만 시험한 기존 CUDA 4명 표본은 순차 12.63초·병렬 14.42초였습니다. CUDA 로그에는 이 GPU의 Tensor Core 부재로 성능이 최적이 아니라는 경고가 있습니다. Vulkan의 입력 512 중간 비교에서도 요청 1개는 26.97초·2개는 26.28초로 병렬화 자체의 추가 이득은 작았습니다. 출력 축약은 8개 중 7개의 전략이 달라져 앱에 반영하지 않았으며 벤치마크에만 남깁니다. 위 측정은 고정된 개인별 상황의 처리량 비교이고, 실제 계산에서 다른 모의 시점의 요청을 미리 묶지 않습니다. 전체 100명 시뮬레이션의 단축률을 보장하지 않습니다.

별도 6개 상황에서도 기존 CUDA 병렬 설정 30.66초 → Vulkan 최적화 병렬 설정 19.78초로 약 35% 짧았습니다. 두 표본의 전략은 14/14 일치했고 이동 선택은 11/14 일치했습니다. 판단 실패는 0건, 전체 회귀 테스트는 87개 통과했습니다. 출력 형식과 정보 분리를 유지해도 실행기의 수치 연산 차이로 모델 선택이 달라질 수 있으므로 새 응답을 별도 설정의 캐시에 기록합니다.

`python scripts/benchmark_local_inference.py --count 8 --batch-sizes 128 512 --workers 1 2 --reset-between-trials`로 새 응답 캐시에서 재측정합니다. 최초의 서버 설정은 `pwsh -NoProfile -File scripts/start_local_ollama.ps1 -Restart -Backend cuda_v13 -Parallel 1 -KvCacheType q8_0`이며, 최초의 앱 설정까지 재현하려면 `PERSONA_EVAC_DECISION_WORKERS=1`, `PERSONA_EVAC_PROMPT_BATCH_SIZE=128`도 적용해야 합니다. 다른 GPU에서는 실행기별 성능을 다시 비교해야 합니다.

## 성향·근거·재현성

정책은 [private_agent_policy.json](configs/agents/private_agent_policy.json), 현재 성향 분류·검증은 [full_profile.py](src/persona_evac/persona/full_profile.py)에 있습니다. [experimental_profile.py](src/persona_evac/persona/experimental_profile.py)는 기존 키워드 후보 방식과 현재 방식의 선택을 함께 지원합니다.

| 실험 성향 | 낮음 / 보통 / 높음의 정책값 |
| --- | --- |
| 혼잡 회피 | 혼잡 비용 0 / 12 / 36 |
| 대기 인내 | 인내 기준 3 / 8 / 16초 |
| 위험 회피 | 위험 비용 배율 1 / 2 / 4 |
| 탐색 적극성 | 탐색 보너스 2 / 6 / 12 |
| 타인 추종성 | 본인이 관측한 이동 흐름에 비례하는 경로 가점 0 / 6 / 18 |
| 추월 적극성 | 낮음은 추월 의도 제한, 보통·높음은 기존 물리 조건 안에서 LLM이 의도 선택 |

정책값은 실험 가정이며 실제 사람에게서 측정한 성격·위기 대응 능력이 아닙니다. 선택 비용과 실제 소요 시간을 구분합니다.

- 현재 Gemma 계산은 UUID를 제외한 전체 페르소나를 읽고 여섯 성향의 등급과 판단 근거 요약만 반환합니다. 키워드 후보나 직접 인용을 분류 조건으로 강제하지 않습니다.
- 주어진 문맥 안에서 판단하며 정보 부족 여부나 별도의 근거 수준은 출력하지 않습니다. 검증은 성향 6개·등급·비어 있지 않은 요약·추가 필드 금지를 확인합니다.
- 후속 상황 판단에는 성향 등급만 전달하고 원문과 분류 요약은 제외합니다. 화면에서는 9개 항목의 요약을 위치 위의 ‘분류 근거’ 하나에 모읍니다.

과거 `keyword_candidates` 방식의 후보 추출·원문 인용·UUID 시드 배정은 이전 자료 비교와 기본 이동 모드의 호환을 위해 남아 있습니다. 현재 전체 원문 분류의 처리 방식과 구분합니다.

프로필은 output/gaehwasan/private_profile_cache 아래 정책 버전 / UUID / 시드 / 입력 해시로 저장합니다. 입력·모델·프롬프트·스키마·추론 설정이 달라지면 이전 응답을 새 결과로 재사용하지 않습니다. 반응·보행·친숙도의 초기 분류 캐시는 별도로 관리합니다.

현재 전체 원문 성향 버전은 full_persona_traits_v3이며 초기 반응·보행·친숙도 분류는 baseline_levels_summary_v4입니다. 기존 키워드 후보 버전은 experimental_traits_v2입니다. 개인 지도·관측·전략 버전은 personal_space_v1 / occluded_perception_v1 / private_strategy_v2이며 결과와 응답 캐시에 실제 프로필 버전·시드·정책·원문 해시를 포함합니다. 전체 결과는 관련 실행 코드 서명도 검사합니다.

## 초기 친숙도와 개인 관측

[gaehwasan_prior.json](configs/agents/gaehwasan_prior.json)은 사전 구조 기억 정책을 정의합니다. 현재 친숙도는 초기 LLM이 전체 생활·거주·직업·이동·이용 문맥을 보고 초행·구조에 익숙함으로 분류합니다. 특정 거주지 키워드 하나로 분류를 고정하거나 정확한 집 위치·역까지의 거리를 추정하지 않습니다.

구조에 익숙한 사람은 실제 역 모델의 모든 계단 위치와 층 연결을 사전 기억으로 갖습니다. 현재 화재·혼잡·통행 가능성이나 미관측 통로의 보행 지도는 주지 않습니다. 과거 거주지 규칙으로 만든 저장 결과는 100명 모두 초행이었으며, 이 수치를 새 LLM 친숙도 분류 결과로 간주하지 않습니다. 과거의 제한적 거주자 기억은 이전 매핑을 읽는 경우에만 사용합니다.

[personal_space.py](src/persona_evac/integration/personal_space.py)는 벽·기둥·층·열차 벽과 문, 거리와 FDS 연기 가림을 검사합니다. 최대 18m 전방향 시야, 2m 관측 지도, 1초 갱신, 연기 광학 감쇠 예산 3, 광선 표본 간격 3m, 현재 관측 유효 시간 3초를 가정합니다.

각자 본 계단·통로·사람과 시점·출처를 기록합니다. 상대 속도는 자신의 연속 관측 위치로 추정합니다. 다른 사람의 목표속도·목적지·계획을 관측값으로 읽지 않습니다. 연결층은 과거 지식이나 직접 이동한 경험으로 배웁니다. 현재 모델에는 의사결정용 안내 표지가 없으며 화면 설명용 라벨은 전달하지 않습니다.

정확한 FDS 온도·소광계수는 물리 계산과 환경 시각화에서 사용합니다. 판단에는 연기 없음/옅음/짙음/시야 차단, 평상시/따뜻함/강한 열감의 단계만 제공합니다. 먼 계단의 열감은 미관측입니다. 과거 관측과 현재 사실을 구분하고 지난 위험의 불확실성 비용을 따로 계산합니다.

## 사건·이동·물리 제약

- 이동 시작·새 경로·대기 증가·정체·관측 위험 상승과 완화·층 이동 때 판단합니다. 일반 판단은 개인당 15초 간격·최대 6회이며 중요한 위험 상승과 층 이동은 한도·간격을 우회합니다.
- 기존 시작 지연 이후에 판단합니다. LLM 대기는 0.5m 이상 이동한 뒤 관측한 대기 맥락이 있을 때만 허용합니다. 대기는 2초, 연속 최대 2회입니다.
- 서두르기는 기본 목표속도의 1.35배, 최대 2.2m/s입니다. 기존 FDS 연기 감속은 계속 적용합니다.
- 현재 추월 의도는 추월 적극성 보통·높음을 허용 조건으로 사용하고 LLM이 상황에 따라 선택합니다. 실행은 빠름 기준, 앞사람과 0.30m/s 이상 차이, 앞사람 속도 비율 70% 이하, 측면 공간과 충돌 조건을 검사합니다. 과거 프로필의 급함·대기 인내·탐색 조건은 이전 형식 호환용 분기로만 남습니다.
- 몸 반경은 0.22m입니다. 현재 계단·개찰구는 JuPedSim의 실제 보행 간격을 검사하며, 과거 FIFO 모델의 고정 1m 간격으로 표시하지 않습니다. 폭에 따른 다중 진입, 진입률·용량·막힌 도착부 제약을 유지합니다.
- 계단 내부 방향 전환·추월·개별 속도 선택은 지원하지 않습니다. 중요한 연기·열감 변화는 판단하되 통행 제약을 기록하고 다음 층에서 재판단합니다.
- 추론 대기 중 모의 시간은 멈춥니다. 실제 계산 대기 시간을 시작 지연이나 대피 시간에 더하지 않습니다.

## 화면·가정·한계

방·개찰구·기둥·벽과 바닥 외곽선은 바닥 깊이를 기록한 뒤 별도 패스로 그립니다. 위층 바닥 뒤의 아래층 구조물·테두리는 가리고, 앞쪽 구조물이 뒤쪽 바닥에 덮여 흐려지는 현상은 방지합니다. 개찰구 본체 14개, 위층의 구조물 가림, B1 아래 B2 외곽선의 가림을 픽셀로 검사합니다. 현재 도면 근사 모델은 개찰 통로 13개와 본체 14개입니다.

B2·B1·1F·출구·열차 안내는 구조물 뒤에 가려지지 않도록 별도 최종 텍스트 패스로 표시합니다. 두 카메라 방향과 차폐 구조물 유무에 따른 픽셀 비교로 여섯 안내의 표시를 확인합니다. 출구·열차 이름 앞의 장식 동그라미 번호는 제거했습니다.

벽은 승객 공간과 접하는 B1 계단 옆 구간만 차분한 회색으로 표시하고 건물을 관통하지 않도록 줄였습니다. B1에는 사용자 빨간 표시의 왼쪽 건물과 북·동·남측 통합 건물만 남겼습니다. 1층에는 곡선 서측 건물과 계단 위·아래 건물 세 곳을 표시합니다. 벽·건물과 구조 바닥의 계단 구멍은 JuPedSim의 보행 영역에서도 제외합니다. 벽 높이 2.1m와 두께 0.18m는 가정입니다.

B1 서측 네 계단은 서로 평행한 직선으로 정렬하고 도착부를 남긴 직사각형 계단 구멍만 표시합니다. 네 계단 사이의 대합실은 하나의 연속된 바닥이며 위·아래 두 쌍의 도착부 사이 연결 바닥도 유지합니다. 방은 보행 불가 영역이지만 구조 바닥에는 구멍을 만들지 않으며 모든 방 아래에 바닥을 유지합니다. 계단참 중앙을 가르던 손잡이는 제거하고 테두리 난간은 유지합니다. 이 조건은 이동 계산을 호출하지 않는 정적 검사와 별도의 B1 평면 화면으로 확인합니다.

2026-10-29 지도 형태를 수정했습니다. B1–1F 연결은 동쪽 한 곳이며, 중앙 손잡이로 분리한 두 하부 계단이 끝부분에서 계단참에 붙습니다. 양옆으로 늘린 계단참 위에서 각각 두 차례 꺾어 하부와 반대 방향의 상부 계단으로 올라갑니다. 계단참은 하부 계단의 끝 단면 및 상부 계단의 시작 단면과 같은 높이·폭으로 맞닿습니다. B1 바닥은 원형 대합실·서측 연결부·승강장 계단 돌출부를 구분하고 계단 개구부 네 곳을 표시합니다. B2–B1 계단 네 곳은 같은 길이이며, 승강장 계단 사이 방과 B1 기능실 위치를 다시 근사했습니다. B1 개찰구 본체는 높이 1m로 표시하며, 13개 통로·0.65m 통로 폭은 도면 근사값입니다.

1층은 사용자 파란 표시의 곡선·출구 바닥을 하나로 연결하고 계단 상부만 열었습니다. 1번 출구는 깔때기 모양의 넓은 바깥 변 전체(도면 근사 약 9.99m)를 나가는 경계로 가정합니다. 2번 출구도 바뀐 바닥 끝 변에 맞췄습니다. `exit_boundary_xy`는 실제 경계, `exit_width_m`는 전체 폭, `width_m`는 양끝의 몸 여유를 둔 연결 유효폭입니다. 외부 지면 높이는 확정하지 않았고 출구는 바닥과 번호만 표시합니다.

현재 설정은 `ready`, `simulation_enabled=true`입니다. 계단·개찰구의 JuPedSim 연결을 구현했으며 API·CLI의 명시적인 실행 요청으로 계산할 수 있습니다. 페이지 조회·새로고침은 계산을 시작하지 않습니다. 직선 계단은 실제 경로 길이를 펼친 2D JuPedSim 영역에서 보행합니다. H_E처럼 꺾인 계단참은 실제 수평 경로와 회전 경유점을 엔진에서 걷고 경사에 따른 속도·높이를 복원합니다. 같은 줄의 펼친 좌표를 꺾인 3D 경로에 압축해 배치하지 않으며, 엔진의 2D 좌표와 표시·관측용 XYZ 좌표를 함께 기록해 몸 간격을 각각 검사합니다. 엔진 자체가 3D 계단 보행을 계산하는 것은 아니며, 계단참의 세부 보행 곡률·단면은 도면 근사입니다. B1은 개찰구의 유료·비유료 쪽으로 분리하고 13개 개찰구 연결만 양쪽을 잇습니다. 통로마다 한 명만 진입할 수 있고 다음 영역이 막히면 점유를 유지하므로 틈을 통한 우회나 통로 안 중복 진입을 허용하지 않습니다. 계단은 B2→B1→1층의 대피 방향으로 연결했습니다.

지도 전용 미리보기 응답·캐시·전용 안내와 보류 화면은 제거했습니다. `/api/gaehwasan/setup`은 현재 지도와 원본 페르소나의 실제 초기 입력만 반환하고 계산 결과를 만들지 않습니다. `/api/gaehwasan`의 GET은 현재 지도 설정·계산 코드·정책과 일치하는 저장 결과만 재생에 제공합니다. 이전 결과는 409, 결과가 없으면 404로 거부하며 화면은 현재 초기 입력과 ‘계산 결과 없음’을 표시합니다. 기존 결과 파일을 새 지도에 맞는 것처럼 다시 표시하거나 해시를 바꾸지 않습니다. 3D 지도·계단 개구부·80:20 배치·공용 초기화·JuPedSim 연결 코드는 유지합니다. 화면의 ‘설정으로 계산’을 명시적으로 누르기 전까지 실제 이동 계산이나 새 AI 호출은 없습니다. `scripts/verify_station_ready.cjs`는 테스트용 POST를 브라우저에서 차단하고 준비 화면·이전 결과 차단·정적 재생 자료 전환을 확인합니다.

## 재현·검사

왼쪽 설정 패널은 대피 인원·화재 시나리오·상황 판단을 항목명과 선택값의 세 행으로 표시합니다. 화재 시나리오는 ‘5호선 열차 화재 / 없음’이며, 계산 상태는 짧게 표시합니다. 화면 표시 설정에는 토글 없이 표시 항목 이름과 선택창을 한 행에 배치하며, 연기 불투명도 조절바는 입체 연기를 선택했을 때만 표시하고 전환 전 값을 유지합니다. 표시 항목은 입체 연기·평면 연기·온도·숨기기입니다. 최종 결과에는 대피 완료·미완료 인원과 출구별 인원을 함께 표시하고 평균 계단 대기는 표시하지 않습니다. 계산 전에는 결과 요약을 숨깁니다. 에이전트 검색을 제거하고 제목 옆의 작은 선택창에서 번호순·속도 빠른순·속도 느린순 정렬을 제공합니다. 속도는 우측 표와 같은 개인별 `desired_speed_mps`를 기준으로 하며, 동률은 번호순, 아직 속도가 분류되지 않은 에이전트는 마지막에 배치합니다. 정렬해도 현재 선택과 재생 시각은 유지하고, 재계산 후에도 선택한 정렬 방식을 유지합니다.

대피 반응 시간·보행 속도·역사 친숙도의 초기 분류는 `baseline_levels_summary_v4`입니다. 전체 페르소나를 읽은 LLM이 세 항목 각각에 `level`과 판단 근거 요약 `assumption`만 반환합니다. 반응·보행 등급은 fast/normal/slow, 친숙도는 first_visit/familiar(초행·구조에 익숙함)입니다. 추월 분류는 성향의 ‘추월 적극성’으로 대체했습니다. 키워드나 직접 인용으로 분류를 제한하지 않습니다. 주어진 문맥 안에서 등급을 결정하고 정보 부족 여부를 설명하지 않습니다. 반응·보행 범주를 경험 자료에 연결해 초·m/s 값을 선택합니다. 웹·CLI의 명시적인 로컬 LLM 대피 계산은 이전 초기값을 메모리에서 새 방식으로 갱신하고 새 응답 캐시를 사용합니다. 원본 `persona_source.json`과 과거 결과는 덮어쓰지 않습니다. 전체 원본 풀을 별도로 준비하려면 `prepare-station-personas`를 사용합니다. 기본 이동 모드는 준비된 초기값을 사용합니다.

성향 카드는 혼잡 회피·대기 인내·위험 회피·탐색 적극성·타인 추종성·추월 적극성의 총 6개이며 모두 낮음·보통·높음입니다. 직업 아래에는 제목 없이 성향 카드를 표시하고, 그 아래 표에 반응 시간·보행 속도·역사 친숙도를 표시합니다. 성향 6개와 표의 3개 항목에 대한 근거는 ‘분류 근거’ 토글 하나에 통합하며 각 이름과 판단 근거 요약만 표시합니다. 이 토글은 표 아래, 위치 바로 위에 배치하고 재생 중 펼침 상태를 유지합니다. 익숙한 사람은 실제 모델의 모든 계단 위치·층 연결을 사전 기억으로 갖고 시작합니다. 현재 혼잡·연기·열·통행 상태와 전체 보행 지도는 제공하지 않으며, 현재 상태는 본인의 관측과 이동으로 갱신합니다. 처음부터 아는 계단도 관측한 보행 지도에 연결되어야 이동 선택지로 사용할 수 있습니다. 과거 거주지 규칙은 이전 매핑의 호환 처리에만 남습니다.

타인 추종성은 본인의 연속 시각 관측으로 추정한 이동 방향만 사용합니다. 현재 시야의 사람 중 같은 보행 영역에서 움직이는 사람의 방향과, 개인 지도에 있는 경로의 첫 이동 방향을 비교합니다. 오래된 관측·첫 관측·다른 층·다른 사람의 목적지나 계획은 사용하지 않습니다. 추종 정도별 가점은 낮음 0초·보통 6초·높음 18초이며 관측한 흐름의 일치도에 비례합니다. 위험·혼잡 등 기존 비용도 함께 적용합니다. 추월 적극성은 보통·높음에서 추월 의도를 허용하고 실제 속도 차이·빈 공간·충돌 제약을 유지합니다.

‘개인이 아는 정보’는 최근 판단 위에 표시합니다. `initial_knowledge`와 재생 시각까지의 `observations`(계단 발견·직접 이동한 층 연결·연기/열감), `people_observations`(시야 안의 사람)을 합쳐 구성합니다. 계단별 출처와 관측 시각은 ‘계단 기억 보기’에 접어 둡니다. 후속 LLM에는 친숙도 등급·아는 층 연결·개인 관측·기억·선택지를 전달하며 친숙도 분류의 근거 요약이나 페르소나 원문은 전달하지 않습니다.

분류 근거 아래 표의 첫 행은 `위치 | 값 | 목표 | 값`으로 표시합니다. 그 아래에 아는 계단, 연기·열감, 관측 시각, 주변 사람을 각각 한 행씩 표시하고, 최근 판단은 계단 기억 토글 다음의 맨 아래 행에 표시합니다. 긴 값은 말줄임하고 마우스를 올리면 전체 값을 표시합니다. 계단 기억 토글도 같은 표 안에 배치합니다. 표 아래에는 ‘페르소나 정보’와 ‘판단 기록’ 토글을 직접 배치합니다. 대피 완료 시 최근 판단 행 대신 표 아래에 완료 시간과 출구를 표시합니다. ‘상세 정보’ 묶음과 그 안의 중복 판단 설명·연구자 수치 표시는 제거했습니다. 판단 기록은 현재 재생 시각까지의 기록만 표시하며 펼침 상태를 재생 중에도 유지합니다.

성향 분류 기본값은 `configs/agents/private_agent_policy.json`의 `profile_classification.default_method`에 있는 `keyword_candidates`입니다. 기존 키워드 후보·LLM 해석·UUID 시드 배정과 `experimental_traits_v2` 캐시는 그대로 사용합니다. 새 설정은 별도 해시를 사용하므로 기존 정책 해시·시드 결과·캐시 키를 바꾸지 않습니다.

`full_persona`는 UUID를 제외한 모든 원본 필드를 이름·값 그대로 Gemma에 전달합니다. 분류 LLM은 여섯 성향 각각에 등급 `level`(low/normal/high)과 한국어 판단 근거 요약 `assumption`만 반환합니다. 주어진 문맥 안에서 등급을 결정하고 정보 부족 여부는 설명하지 않습니다. 여섯 성향과 두 필드의 존재, 유효한 등급, 비어 있지 않은 요약을 검사하고 다른 출력 필드는 거부합니다. 입력 문장 선별이나 성향별 후보 수 제한은 없습니다. 분류의 의미 타당성 자체는 LLM 판단입니다.

후속 상황 판단 LLM에는 성향별 `level`만 전달하며 분류 원문·근거 요약·근거 수준·인용·분류 메타데이터는 전달하지 않습니다. 현재 관측·개인 기억·알고 있는 이동 선택지는 기존처럼 전달합니다. 근거 요약은 저장 결과와 화면의 통합 ‘분류 근거’ 토글에만 남습니다. 웹 화면에서 로컬 Gemma로 계산하면 `full_persona`를 명시적으로 요청하고, 기본 이동 모드는 기존 `keyword_candidates`를 사용합니다.

활성 결과를 바꾸지 않고 새 방식 100명을 준비하고 기존 캐시·5명 3회 추정을 비교하려면 다음을 실행합니다.

```powershell
docker compose exec -T app python scripts/prepare_private_profiles.py --method full_persona --count 100 --compare --repeat-count 5 --repeat-runs 2
```

별도 결과는 `output/gaehwasan/profile_preparations/full_persona/full_persona_traits_v3/profiles.json`, 집계·실패·반복 기록은 같은 폴더의 `report.json`입니다. 기본 캐시는 `private_profile_cache/full_persona_traits_v3` 아래에 원본·실험 시드·모델 이름/다이제스트·정책/프롬프트·스키마·추론 설정으로 구분됩니다. 이전 분류 캐시와 기존 상황 판단 응답은 새 형식의 응답으로 재사용하지 않습니다. 반복 표본은 별도 `repeats` 경로에 저장됩니다. 같은 명령을 다시 실행하면 준비된 결과를 재사용합니다. 독립 재추론이 필요하면 별도 `--output-root`와 `--source`를 지정합니다.

기존 결과·캐시 해시 보존, 두 방식의 캐시 재사용, 원문·인용·정보 부족 실제 표본, 반복 등급 변화를 전수 검사하려면 `docker compose exec -T app python scripts/audit_profile_preparation.py`를 실행합니다. 이 검사는 추론이나 대피 계산을 호출하지 않습니다. 결과는 준비 폴더의 `verification.json`이며 변경 파일 목록과 한계도 포함합니다. 최초 보존 기준은 이번 구현 전에 기록한 `output/gaehwasan/profile_baseline_manifest.json`입니다.

선택 우선순위는 명시적 `--method`(준비 스크립트) / `--profile-method`(실행 CLI) / API의 `profile_method`, 환경변수 `PERSONA_EVAC_PROFILE_METHOD`, 정책의 기본값 순서입니다. API·CLI의 실행 요청은 대피 계산이므로 성향만 준비할 때는 위 스크립트를 사용합니다. 분류 방식·버전·프로필 정책 해시가 새 실행 결과에 기록됩니다. 판단 프롬프트는 두 방식 모두 등급만 받으며 전체 방식의 판단 캐시는 별도 경로를 사용합니다. 기존 프로필에는 호환성을 위해 메타데이터를 덧붙이지 않으며, 방식 표시가 없는 과거 결과는 기존 방식으로 읽습니다.

전체 입력은 자르지 않습니다. UTF-8 바이트 수를 이용한 보수적 입력 예산에 출력·스키마·메시지 여유를 포함하고 모델 지원 문맥을 확인합니다. 한도 초과는 `context_overflow`, 통신 오류는 `communication_error`, 등급·요약·출력 형식 오류는 `invalid_output` 등의 기술 실패로 기록합니다. 형식 검증 재시도에도 원문 전체를 유지하며, 실패를 정상 추정이나 시드 배정으로 저장하지 않습니다. 오류 시 일부 완료된 사람의 캐시는 재사용 가능하지만 준비 보고서 상태는 실패입니다.

화면의 ‘분류 근거’는 성향 6개·반응 시간·보행 속도·역사 친숙도에 해당하는 9개 이름과 근거 요약만 표시합니다. 저장 결과 조회(`GET /api/gaehwasan`)는 활성 결과를 재계산하거나 덮어쓰지 않습니다. 코드·정책이 달라진 이전 결과는 409 응답을 반환하고 화면은 계산 전 상태로 전환합니다. 재계산은 명시적 실행 요청으로만 수행합니다.

프로젝트 루트에서 실행합니다. 기존 FDS 결과를 다시 계산할 필요는 없습니다.

```powershell
docker compose run --rm --no-deps -v "${PWD}:/workspace" -w /workspace -e PYTHONPATH=/workspace/src --entrypoint python app -m persona_evac.cli run-gaehwasan --agent-count 100 --fire --qwen --experiment-seed 20261027 --output output/gaehwasan/reproduced.json
docker compose run --rm --no-deps -v "${PWD}:/workspace" -w /workspace -e PYTHONPATH=/workspace/src --entrypoint python app scripts/audit_private_result.py output/gaehwasan/reproduced.json
```

개발 검사는 pytest를 사용합니다. 미관측 경로·위험·다른 사람 계획의 변경에 대한 불변성, 새 관측·막힌 경험, 친숙도별 계단 기억, 중요 사건의 한도 예외, 측면 진입·충돌 회피를 검사합니다. test 이미지에 output을 연결하면 기존 FDS를 쓰는 검사도 실행합니다. 화면 검사는 scripts/verify_private_ui.cjs에서 통합 분류 근거 9개, 제목 제거, 위치 순서와 재생 중 토글 유지를 확인하고 우측 패널 캡처를 저장합니다. T자 복도 검사는 scripts/verify_simulation_views.cjs입니다.

FDS 좌표축·층·시간·계단 높이 보간과 입력 검증의 단위 테스트는 tests/fds_fixture.py의 독립적인 합성 2층 공간을 사용합니다. 과거 역 설정이나 실제 FDS 결과 파일 없이 실행하며, 실제 개화산역 FDS 연동 검사는 별도로 유지합니다.
